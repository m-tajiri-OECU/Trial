# 購買エージェント 進め方ガイド

原則: **エージェントは「準備と提案」まで。発注の確定・承認は人が行う。**

## 推奨ステップ

| 段階 | 内容 | 状態 |
|---|---|---|
| 0 | 現行フローの課題整理・基準の確認(金額閾値、承認ルート、相見積/入札の要否) | 要・現場確認 |
| 1-a | 依頼受付 + 振り分け + 承認ルート + 予算警告(ルールベース) | **実装済** |
| 1-b | 自然文の品目抽出をLLM化(I/Fは `src/triage.js` を維持) | 次 |
| 1-c | サイト系: 価格・納期の比較、カート/発注一覧の準備 | 次 |
| 2 | 見積系: 依頼文ドラフト、見積PDFの読取・比較表、選定理由書 | |
| 3 | 納品・検収・三者照合・財務システム連携 | |
| 4 | ガバナンス: 操作ログ、分割発注・重複購入の検知、支出分析 | 1-aと並行して着手推奨 |

## なぜ「依頼受付 + 振り分け」から始めるか

1. 以降すべての機能の入口で、ここで集めた構造化データ(品目・数量・金額・予算科目)が後工程の土台になる。
2. LLMなしのルールで動くため、挙動が説明可能で、規程との突合がしやすい。
3. 閾値や承認ルートを早期に現場へ見せられ、フィードバックで基準の曖昧さが洗い出せる。

## 次に決めること(段階0)

- 金額別の手続き・承認ルートの正式基準(現在は `data/rules.json` の仮置き値)
- 標準品リスト・契約単価品の元データ(現在は `data/standard-items.json` のダミー)
- 予算データの取得元(財務システムのCSV出力か、API連携か)
- 認証(現在は未実装。依頼者・承認者の識別にはSSO連携が必要)
- 永続化(現在はJSONファイル。依頼の保存・ログには DB が必要)

## 設計メモ

- 判定ロジックは純関数(`src/triage.js`)に分離済み。LLM化・テスト追加が容易。
- 操作ログは最初から設計に含める(監査対応)。依頼保存を実装する段階で追加する。
